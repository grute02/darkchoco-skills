# ⑥ 툴킷 (래퍼)

툴킷 파일을 고치지 않고 호출할 때 우리 기준을 지시한다.
툴킷은 3기 자산이라 수정 승인이 어렵다. 그래서 출력 기준을 프롬프트로 얹는다.

| 불일치 | 툴킷 | 우리 기준 |
|---|---|---|
| 판정 축 | 5단계 하나 | **다섯 축** |
| 재포장 | 진위 판정에 포함 | 신규성 재유포 |
| 검증 항목 | 8항목 평면 | 핵심 4 + 보조 7 |
| 분류 | 없음 | A~D |
| 위험도 | 5항목 0~5점 총점 | **5항목 상태값. 총점 없음** |
| 임계값 | 없음 | 단가·샘플비율·규모 대 이용자 |

```
$threat-intelligence-report-ko

[목적]
이 유출 주장의 진위를 판정하기 위한 근거를 정리한다.
결론을 단정하지 말고 항목별 상태와 계산 결과를 산출한다.

[재료]
(⑤ 재료 합치기 출력을 그대로 붙여넣는다)

[출력 기준 — 이 프로젝트 전용]
아래 규칙을 툴킷 기본 출력보다 우선 적용한다.

1. 판정을 다섯 축으로 분리해서 낸다. 하나로 합치지 않는다.
   각 축의 기준은 아래와 같다. 이 기준 밖의 값을 쓰지 마라.

   [검증 분류] 사건을 밖에서 누가 확인해 줬는지. 데이터 진위와 별개다.
     A : 규제기관 또는 수사기관이 조사 후 사실관계를 확정
     B : 피해 조직이 침해 또는 유출 사실을 공식 발표
     C : 독립된 제3자가 게시글 밖의 사실을 하나 이상 추가해 공개했으나
         조직 확인은 없음
     D : 게시글 밖 사실을 추가한 자료가 없음

     ※ C는 발행 주체가 언론인지 보안업체인지 연구자인지 묻지 않는다.
       무엇을 확인했는지만 본다
     ※ 게시글 내용을 옮겨 적기만 한 알림·요약·재게시는 계상하지 않는다
     ※ 추가된 사실이 사건과 무관하면(일반적 업계 해설, 대응 권고) 계상하지 않는다
     ※ 여러 개에 해당하면 A에 가까운 쪽을 쓴다
     ※ 조직이 반박해도 사건 출처가 다크웹 게시글이면 D다
     ※ 판정 신뢰도와 다른 값이다. 섞지 마라

   [C 계상 판정 보조 질문]
     1에서 4 중 하나라도 예이고 5도 예이면 계상한다.
     1. 게시글에 없는 데이터 관측을 제시했는가
        (행 수, 값 패턴, 필드 분포, 파일명, 용량)
     2. 게시글에 없는 외부 대조 결과를 제시했는가
        (과거 유출본, 다른 게시글, 인프라·식별자 재사용)
     3. 게시글에 없는 당사자 발언을 인용했는가
        (조직, 규제기관, 판매자 접촉)
     4. 게시글의 특정 주장을 반증 또는 확증하는 확인 절차를 기술했는가
     5. 그 관측을 우리가 재현하거나 확인할 수 있는가

     ※ 5번은 AI가 생성한 알림 기사가 없는 관측을 지어내는 것을 막는다.
       1에서 4가 예여도 재현할 수 없으면 계상을 보류한다
     ※ 자료를 읽고 판단한다. 링크 개수로 세지 마라

   [진위 판정] 게시된 데이터가 실제 데이터인가.
     확인됨      : 피해 조직·규제기관이 공식 확인.
                  또는 핵심 4항목이 모두 충족되고 독립 검증까지 확인됨
     신뢰성 높음  : 핵심 4항목 중 3개 이상이 충족 또는 부분충족이고,
                  불충족과 공식 반박이 없음
     미확인      : 충족과 부분충족을 합쳐 2개 이하이거나,
                  확인불가 항목이 많아 판단이 어려움
     신뢰성 낮음  : 내용·규모·조직 내부 체계 불일치,
                  합성·AI 생성·과장 등 신뢰 저하 정황이 확인됨
     허위        : 피해 조직·기관이 구체적 근거와 함께 반박,
                  또는 데이터 조작·합성 사실이 확인됨
     ※ 부분충족은 신뢰성 판단에는 쓰되
       「확인됨」 판정에서는 충족으로 계산하지 않는다

   [신규성 판정] 새롭게 유출된 데이터인가.
     신규 유출   : 최신 데이터가 확인되고 기존 동일 데이터의 선행 유통이 없음
     재유포      : 기존 유출본과 파일·레코드 구조가 동일
     혼합        : 과거 데이터와 신규 데이터가 함께 포함
     확인불가    : 데이터 날짜·과거 자료가 부족
     ※ 재유포라도 데이터가 실제면 진위는 확인됨 또는 신뢰성 높음이다

   [판정 신뢰도] 이 판정을 얼마나 확신하는가.
     높음 : 공식 자료 또는 복수의 독립 증거가 있고 반대 증거가 없음
     중간 : 샘플 등 일부 직접 증거는 있으나 전체 규모·신규성이 확인되지 않음
     낮음 : 게시글·스크린샷 등 제한된 자료만 있거나 상충 정보가 많음
     ※ 게시글을 직접 열람하지 않고 기사·리스트업만으로 판정한 경우
       높음을 쓰지 않는다

   [위험도] 사실이라면 얼마나 위험한가. 진위와 독립이다.
     자산 민감도       치명 / 높음 / 중간 / 낮음 / 확인불가
     즉시 악용 가능성   가능 / 조건부 / 불가 / 확인불가
     신선도            3개월 이내 / 1년 이내 / 1년 초과 / 확인불가
     피해 범위         대상 조직만 / 제3자 포함 / 확인불가
     확산 정도         무료 공개 / 판매 중 / 재유포 / 확인불가

     ※ 총점을 내지 마라. 항목별로만 낸다
     ※ 증거 강도를 위험도에 넣지 마라. 진위와 판정 신뢰도가 그 역할이다
       미확인이라고 위험도를 깎으면 실제 위험을 과소평가하게 된다
     ※ 진위 미확인 + 위험도 치명은 사실이면 치명이라는 뜻이다.
       확인 우선순위가 가장 높다
     ※ 항목마다 근거 한 줄을 붙인다

     자산 민감도 판정 근거 (파일 트리가 있을 때)
       치명  즉시 악용 가능한 자격증명
             .git/config, .env, .npmrc, id_rsa, *.pem, *.p12
       높음  내부 접근 경로
             *.tf, *.kubeconfig, docker-compose*, 설정 파일 안의 사내 URL
       높음  개인 식별
             실명·이메일이 든 파일명, 커밋 작성자, CODEOWNERS
       중간  사내 소스
             package.json 의 private true, 사내 스코프 패키지
       중간  업무 맥락
             커밋 메시지의 티켓 번호, 브랜치명
       낮음  공개돼도 무해
             README, LICENSE, 락파일

       ※ 등급을 하나로 합치지 마라. 치명 1건과 중간 500건은 성격이 다르다.
         등급별 건수를 그대로 낸다

   ※ 다섯 축은 서로 어긋나도 된다.
     분류가 D인데 진위가 신뢰성 높음일 수 있다.
     진위가 미확인인데 위험도가 치명일 수 있다.

2. "과거 자료 재포장"을 진위 판정에 넣지 마라.
   재유포는 신규성 판정이다. 데이터가 실제인데 다시 올린 것일 수 있다.
   그 경우 진위는 확인됨 또는 신뢰성 높음이고 신규성이 재유포다.

3. 검증 항목을 핵심과 보조로 나눠서 낸다.
   핵심 4항목 (각각 충족 / 부분충족 / 불충족 / 확인불가)
     - 대상 일치 : 조직명·국가·업종·도메인·서비스가 실제 대상과 일치하는가
                   ※ 이 항목만 3단계다. 충족 / 불충족 / 확인불가
                   ※ 트리가 있으면 사내 전용 패키지 스코프, 내부 URL 도메인,
                     커밋 작성자 이메일 도메인이 근거가 된다
     - 샘플 검증 : 샘플이 존재하고 정상적으로 분석 가능한가
                   ※ 실물 트리는 샘플보다 강한 증거다. 구조 전체는 부분 위조가 어렵다
                   ※ 게시글 헤더를 범주로 묶은 구조 도식은 샘플이 아니다
                   ※ 침투 경로 추정 서술은 샘플이 아니다. 값으로는 도출되지 않는다
     - 내용 일치 : 게시글 주장과 샘플의 필드·값이 일치하는가
                   ※ 트리가 있으면 주장 항목이 실제 파일 구성에 있는지 본다
     - 규모 검증 : 주장 레코드 수·용량·사용자 수가 현실적인가
                   ※ 트리가 있으면 파일 수, 용량, 커밋 수와 대조한다
   보조 7항목 (관측된 것만)
     - 형식 / 값 / 중복 / 원천 / 평판 / 피해성 / 게시위치
       ※ 형식  트리가 있으면 파일 구조가 그 조직 기술 스택과 맞는지
       ※ 중복  파일 목록을 해시로 만들어 과거 유출과 대조
       ※ 원천  정상 릴리즈 프로세스 흔적. 티켓 번호, PR, 태그
       ※ 피해성 위험도 다섯 항목이 여기 붙는다

4. 계산을 반드시 포함한다.
   - 레코드당 단가 = 가격 ÷ 주장 규모
   - 샘플 비율 = 샘플 행 수 ÷ 주장 규모
   - 규모 대 이용자 = 주장 규모 ÷ 알려진 이용자 수
   대체값을 쓴 항목은 대체 사실과 근거를 함께 적는다.
   분모를 확인하지 못했으면 계산하지 말고 못 봄으로 적는다.

5. 아래 세 가지를 보조 항목에서 반드시 확인한다.
   - 게시위치 : 압수·폐쇄된 플랫폼을 출처로 표기했는지
                (원본 BreachForums, RAMP, LeakBase, Nulled, Indra/N/A BF)
   - 원천     : 무관한 조직의 게시글에 같은 판매자 핸들이 나오는지
   - 형식     : 무관한 조직의 게시글과 필드 구성이 거의 같은지

6. 파일을 받지 않으므로 원본 파일 해시 대조를 요구하지 마라.
   파일명·용량·필드 구성·게시 시각으로 대신한다.
   트리를 확보한 경우에는 파일 목록 자체를 해시로 만들어 대조할 수 있다.
   그래도 모르면 못 봄으로 둔다.

7. 트리에서 자격증명이 보여도 살아있는지 확인하라고 요구하지 마라.
   남의 자격증명을 실제로 쓰는 행위다. 존재와 패턴까지만 적는다.

[출력 형식]
아래 번호 순서 그대로 낸다. 각 블록 끝의 화살표는 어느 칸으로 가는지다.
1번에서 8번은 검증 DB 재료다. 9번은 수집 DB 재료다.
순서를 바꾸지 마라.

1. 계산
   단가 / 샘플 비율 / 규모 대 이용자. 대체값 사용 여부 표시
   → 검증 자료

2. 핵심 4항목
   항목별 상태 + 근거 한 줄
   → 핵심 검증 결과 · 검증 요약 첫 줄

3. 보조 항목
   관측된 것만. 없으면 생략
   게시위치·원천·형식 세 가지는 관측 여부를 반드시 적는다
   → 검증 요약

4. 반대 증거
   현재 정황과 충돌하는 사실. 없으면 "없음"이라고 적는다
   → 검증 요약 · 한계

5. 참고 판정 (다섯 축)
   검증 분류 / 진위 / 신규성 / 신뢰도 / 위험도
   각각 근거 한 줄. 단정하지 말고 "현재 재료로는" 을 전제로 적는다
   위험도는 다섯 항목을 각각 낸다. 총점을 내지 마라
   → 검증 분류 · 진위 판정 · 신규성 판정 · 판정 신뢰도 · 위험도 다섯 칸

6. 판정이 바뀔 조건
   어떤 정보가 추가되면 어느 축이 어떻게 바뀌는지
   → 판정 변경 조건

7. 한계
   판정에 필요한데 재료에 없는 것. 왜 못 봤는지 함께
   → 한계

8. 권고
   이 정보를 받는 사람이 자기 자리에서 무엇을 할 수 있는지 적는다.
   정보를 나열하고 끝내면 조사 메모지 보고서가 아니다.

   세 갈래로 나눈다. 해당 없으면 그 줄을 적지 않는다.

     추가 조사 가능한 것
       우리가 더 확인할 수 있는 것. 판매자 다른 게시글, 후속 링크 큐, 미열람 자료
     확인이 필요한 것
       대상 조직이 자기 시스템에서 대조해야 하는 것.
       게시글에 나온 테이블명·필드명이 실제 운영 DB와 맞는지,
       주장 시점 전후의 대량 조회·내보내기 기록,
       관리자 계정 비정상 로그인
     즉시 조치가 필요한 것
       사실 여부와 무관하게 지금 할 수 있는 것.
       거래처 사칭 메일 주의 안내, 결제계좌 변경 요청 확인 절차,
       고객 문의 대응 문구 준비

   → 검증 요약 끝 또는 별도 보고

9. 수집 DB 입력안
   **판정을 기다리지 않는다.** 수집 DB 에는 판정 칸이 없다.
   ⑦⑧ 이 끝나기 전에 넣어도 되고, 넣어야 다음 건에서 중복 대조가 된다.
   여기서 안 내면 조사한 건이 팀 DB 에 안 남는다.

   ⑤ 재료 합치기 출력을 옮긴다. 칸 이름과 순서는 stage9-db.md 의 ⑨-1 을 따른다.
   판정·신뢰도·위험도는 넣지 마라. 그 칸이 없다.

   `중복 관계` 와 `같은 사건` 은 ③ 사전 확인에서 도구가 낸 분류를 옮기되
   **도구 분류라고 표시한다.** 확정은 사람이 한다.
```
