# 3. 개정 상세

## 3-1. 위험도 축 신설

**전.** 네 축. 검증 분류, 진위, 신규성, 신뢰도. 위험도 없음.
**후.** 다섯 축. 위험도 추가.

툴킷 `references/verification.md` 에서 가져와 다섯 군데 고침.

| | 툴킷 | 왜 고쳤나 | 우리 것 |
|---|---|---|---|
| 1 | 증거 강도 포함 | 진위·신뢰도와 축이 섞임 | 뺌 |
| 2 | 총점 | 우리는 축을 합치지 않음 | 총점 없음 |
| 3 | 0~5점 | 재현 안 됨 | 상태값 |
| 4 | 신선도 정의 없음 | 신규성과 겹침 | 데이터 기준 시점으로 한정 |
| 5 | 제3자 피해 없음 | 고객사 혼입이 파장을 가름 | 피해 범위 신설 |

**1번이 핵심.** 원본대로면 미확인 건은 위험도가 같이 깎여 실제 위험을 과소평가.

    진위 미확인 + 위험도 치명   사실이면 치명. 확인 우선순위 최상
    진위 확인됨 + 위험도 낮음   진짜지만 급하지 않음

**최종 다섯 항목.**

| 항목 | 상태값 |
|---|---|
| 자산 민감도 | 치명 / 높음 / 중간 / 낮음 / 확인불가 |
| 즉시 악용 가능성 | 가능 / 조건부 / 불가 / 확인불가 |
| 신선도 | 3개월 이내 / 1년 이내 / 1년 초과 / 확인불가 |
| 피해 범위 | 대상 조직만 / 제3자 포함 / 확인불가 |
| 확산 정도 | 무료 공개 / 판매 중 / 재유포 / 확인불가 |

총점 없음. 항목마다 근거 한 줄.

**자산 민감도 판정표.**

| 등급 | 파일명 신호 |
|---|---|
| 치명 | .git/config, .env, .npmrc, id_rsa, *.pem, *.p12 |
| 높음 | *.tf, *.kubeconfig, docker-compose*, 사내 URL |
| 높음 | 실명·이메일 파일명, 커밋 작성자, CODEOWNERS |
| 중간 | package.json private true, 사내 스코프 패키지 |
| 중간 | 커밋 티켓 번호, 브랜치명 |
| 낮음 | README, LICENSE, 락파일 |

등급을 합치지 않음. 등급별 건수를 그대로 냄.

## 3-2. 검증 분류 C 개정

**전.** `신뢰할 수 있는 언론이 독립 취재로 보도했으나 조직 확인은 없음`
**후.** `독립된 제3자가 게시글 밖의 사실을 하나 이상 추가해 공개했으나 조직 확인은 없음`

**왜.** 현행은 누가 냈나를 묻는데 이 축이 재려는 것은 무엇을 확인했나.
벤더 알림을 언론이 아니라서 제외하면 같은 내용을 언론이 내면 C가 됨.

**단서 셋.**

    발행 주체가 언론인지 보안업체인지 연구자인지 묻지 않는다
    게시글 내용을 옮겨 적기만 한 알림·요약·재게시는 계상하지 않는다
    추가된 사실이 사건과 무관하면 계상하지 않는다

## 3-3. C 계상 보조 질문 5개

1에서 4 중 하나라도 예이고 5도 예이면 계상.

    1. 게시글에 없는 데이터 관측을 제시했는가
    2. 게시글에 없는 외부 대조 결과를 제시했는가
    3. 게시글에 없는 당사자 발언을 인용했는가
    4. 게시글의 특정 주장을 반증 또는 확증하는 확인 절차를 기술했는가
    5. 그 관측을 우리가 재현하거나 확인할 수 있는가

**5번이 신설.** AI 생성 알림이 없는 관측을 지어내면 1번에 예가 됨.
실제로 이번 건 기사 하나는 저자가 사람이 아니었고 실행 불가 명령을 실음.

자료를 읽고 판단. 링크 개수로 세지 않음.

## 3-4. 파일 트리를 새 입력 유형으로

| | 판매글, 샘플 | 파일 트리 |
|---|---|---|
| 누가 고름 | 판매자 | 구조 전체 |
| 조작 난이도 | 쉬움 | 어려움 |
| 값을 봐야 하나 | 봐야 함 | **안 봐도 됨** |

**값을 안 봐도 되는 것이 핵심.** 마스킹 없이 원문 분석 가능. 자동화가 붙음.

**계상 기준.**

| 무엇 | 계상 |
|---|---|
| 판매자가 올린 트리 캡처 | 게시글 내용. 안 셈 |
| 우리가 확보한 실물 트리 | 게시글 밖 사실. 계상 |

**마스킹.** 트리는 마스킹 대상 아님. 값이 아니라 이름과 구조. 마스킹하면 분석이 망가짐.
파일명 자체에 개인정보가 있으면 **산출물에 실을 때만** 가림.

    분석   scorecards/docs/홍길동_연봉.xlsx
    출력   scorecards/docs/홍○○○○○.xlsx

**기존 항목에 붙는 근거.**

| 항목 | 트리에서 |
|---|---|
| 대상 일치 | 사내 패키지 스코프, 내부 URL, 커밋 작성자 도메인 |
| 샘플 검증 | 실물 트리는 샘플보다 강한 증거 |
| 내용 일치 | 주장 항목이 실제 파일 구성에 있는가 |
| 규모 검증 | 파일 수, 용량, 커밋 수 |
| 형식 (보조) | 구조가 조직 기술 스택과 맞는가 |
| 중복 (보조) | 파일 목록 해시로 과거 유출 대조 |
| 원천 (보조) | 티켓 번호, PR, 태그 |
| 피해성 (보조) | 위험도 다섯 항목 |

**하면 안 되는 것.** 토큰이 보여도 살아있는지 요청 보내지 않음. 존재와 패턴까지만.

## 3-5. 샘플 계상 기준

**샘플이 아닌 것.**

| 무엇 | 왜 |
|---|---|
| 게시글 헤더를 범주로 묶은 구조 도식 | 레코드가 없음. 행, 값, 건수, 결측, 분포 전부 없음 |
| 침투 경로 추정 서술 | 데이터 값으로 도출 안 됨. 관측이 아니라 추정 |
| 게시글 내용 요약 | 게시글 밖 사실 없음 |

**샘플로 계상하려면 하나 이상.**

    샘플 행 수
    마스킹한 값 예시 또는 값 패턴
    파일에서 추출한 필드명. 게시글 헤더 아님
    파일명, 용량
    특정 레코드 인용 또는 대조 결과

같은 기준을 파일 트리에도 적용.

## 3-6. 검색 방식 개선 여덟

| | 전 | 후 | 절 |
|---|---|---|---|
| 1 | 안 나오면 없음 | **못 봄 — 수단, 질의, 일시** | 3-6 |
| 2 | 범용 검색만 | **발행처 조회.** 조건부. 검색엔진 우회 | 3-7 |
| 3 | 비슷한 것을 대상으로 | **문자 단위 대조.** 유사 상호 금지 | 3-8 |
| 4 | 단일 수단 0건으로 확정 | **검증 분류 근거로 안 씀** | 3-6 |
| 5 | 식별자를 한 줄에 다 넣음 | **질의를 나눔** | 3-10 |
| 6 | 순서 없음 | **4단계 순서** | 3-11 |
| 7 | 검색 결과를 그대로 채택 | **열어서 문자열 확인 후 채택** | 3-12 |
| 8 | 질의를 계속 변형 | **중단 조건** | 3-13 |

5에서 8은 2026-08-19 검토안 2에서 왔다.

**폐기한 것.** 검색 결과에 질의 문자열이 있는지 확인하고 없으면 수단을 바꾸는 자가 점검.
매 질의마다 사람이 판단하는 절차라 불가능. 바꿀 수단이 없는 팀원에게는 막다른 길.

**교훈.** 프롬프트로 검색 성능은 못 올림. 프롬프트가 할 수 있는 것은 둘.

    부재 주장의 강도를 낮추고 근거를 남기게 함
    검색에 의존하지 않는 고정 경로를 박음

**뺀 이유 셋.**

    목록은 낡는다. 새 발행처가 계속 생긴다
    목록에 있는 발행처가 모든 사건을 다루지 않는다. 대부분의 조회가 헛돈다
    목록에 올라간 발행처 쪽으로 자료 수집이 편향된다

**질의 형식.**

    https://<발행처 도메인>/?s=<대상 도메인 또는 조직명>

**왜 되나.** 이 검색 결과 페이지는 `noindex`. 검색엔진에 원리적으로 안 잡힘.
직접 호출해야만 보임. 인덱스 커버리지와 독립. 크레딧 안 듦.

**조건 둘.**

| 조건 | 무엇을 조회하나 |
|---|---|
| 검색 결과나 재료에서 발행처가 하나라도 확인됨 | 그 발행처 내부 검색을 이어서 |
| 범용 검색이 0건 | 노션 관리 목록을 돌린다. 마지막 경로 |

둘째 조건은 이번 판에서 더한 것이다. 첫째만 두면 구멍이 생긴다.
i-mall 건이 정확히 그 경우였다. 범용 검색이 아무것도 못 찾아 발행처 자체가 확인되지 않았다.
고정 목록의 실제 가치가 **아무것도 못 찾았을 때의 마지막 경로**였다.

0건일 때만 쓰므로 편향 문제는 훨씬 작아진다.

**기록 3분류.** 해당 있음 / 해당 없음 / 조회 실패.
조회 실패를 해당 없음으로 안 적음.

**노션 관리 목록.** 프롬프트가 아니라 별도 자료로 둔다.
`/?s=` 는 워드프레스 경로라 발행처마다 다르므로 칸을 셋으로 둔다.

| 도메인 | 검색 URL | 동작 확인 |
|---|---|---|
| brinztech.com | /?s= | 동작. 목표 문서 1건, 노이즈 0 |

| undercodenews.com | 미확인 | 조회 실패. 응답 본문 없음 |
| dexpose.io | 미확인 | |
| breachsense.com | 미확인 | |
| haveibeenransom.com | 미확인 | |
| darkwebinformer.com | 미확인 | |

| socradar.io | 미확인 | |

실측 3곳 중 2곳에서 유효한 답. 완전하지 않아 3분류 필수.

## 3-10. 질의를 섞지 않는다

**문제.** 한 질의에 식별자 넷을 넣었다.

    Databasehooligan 742k South Korea i-mall business contacts leak

판매자 핸들, 주장 규모, 대상 도메인, 데이터 종류가 한 줄에 있다.

**왜 안 되나.** 자료 종류마다 담고 있는 식별자가 다르다.

| 자료 종류 | 핸들 | 규모 | 도메인 | 필드 구성 |
|---|---|---|---|---|
| 언론 기사 | 안 적는 경우 많음 | 적음 | 적음 | 요약해서 적음 |
| 벤더 알림 | 안 적음 | 안 적는 경우 있음 | 적음 | 상세히 적음 |
| 집계 계정 게시물 | 적는 경우 있음 | 적음 | 적음 | 안 적음 |

실측으로 목표 벤더 알림에 `Databasehooligan` 도 `742k` 도 없었다.
넷 중 둘이 없는 문서는 상위로 못 온다.

**식별자를 많이 넣을수록 정확해지지 않는다. 어느 자료도 만족 못 시키는 질의가 된다.**

## 3-11. 검색 순서 4단계

각각 별개 질의로 돌린다. 한 질의에 섞지 않는다.

| | 질의 | 무엇이 걸리나 |
|---|---|---|
| 1 | 대상 도메인 단독. 따옴표로 묶음 | 벤더 알림, 집계 게시물 |
| 2 | 대상 도메인 + 영문 1단어 (breach, leak, database) | 위와 같되 범위를 좁힘 |
| 3 | 판매자 핸들 단독 | 판매자 추적 자료 |
| 4 | 주장 규모 + 국가 | 규모를 적은 언론 보도 |

## 3-12. 문서 채택 시 리터럴 확인

    채택하려는 문서는 열어서 대상 문자열이 실제로 들어 있는지 확인한다
    없으면 그 문서를 버린다

**폐기했던 자가 점검과 다르다.**

| | 폐기한 안 | 이 안 |
|---|---|---|
| 대상 | 검색 결과 전체 | 채택하려는 문서 하나 |
| 판단 | 사람이 수단을 바꿀지 결정 | 문자열 유무만 보고 버림 |
| 실행 | 매 질의마다. 불가능 | 기계적 |

3-8의 유사 도메인 오채택을 막는다.

## 3-13. 중단 조건

    공식 출처 1건과 독립 출처 1건을 확보하면 멈춘다
    0건이면 사용한 수단명을 적고 멈춘다
    질의를 무한히 변형하지 않는다

## 3-14. 후속 링크 큐

**문제.** 조사 중 나온 미확인 링크를 담을 칸이 없어 다음 확인 항목에 임의로 넣었다.

**신설.**

    조사 중 나온 미확인 링크는 아래 세 항목으로 적는다
      URL / 발견 위치 / 관련 가능성의 근거
    본 판정의 근거로 쓰지 않는다. 다음 조사의 입력이다
    열어보지 않은 링크를 열어본 것처럼 적지 않는다

**어느 단계 출력에 넣을지는 팀 결정이다.** ⑤ 재료 합치기, ⑧ 판정, 별도 중 하나.
현재 안은 ⑤다.

## 3-8. 대상 문자열 일치

    도메인은 문자 단위로 대조한다
    하이픈 위치나 TLD가 다르면 다른 조직이다
    유사 상호나 유사 도메인이 나와도 대상으로 바꾸지 않는다
    특정 못 했으면 특정 못 했다고 적는다

## 3-9. 상태값 표기 통일

| 표기 | 뜻 |
|---|---|
| 확인함 | 봤고 값이 있다 |
| 없음 | 봤는데 없다 |
| 못 봄(이유) | 막혔다. 이유에 수단과 질의 |
| 안 봄 | 이번 범위가 아니었다 |

**빈칸 금지.** 못 본 것을 없음으로 적으면 나중에 실제로 빈 것으로 읽힘.

두 케이스가 여기서 만남.

    다이나트레이스   트리에 있는데 확인 못 한 것
    i-mall          검색으로 못 찾은 것

# 중복 분류 재정의 (2026-08-21)

AT&T 건을 다시 보다가 나왔다. 수집 DB 의 Tanaka 줄(Darkforums, 2025-06)과
MajorNelson 게시글(BreachForums, 2024-03)은 같은 유출인데 행위자와 포럼만 다르다.
옛 분류는 이것을 `다른 게시자 재유포 후보` 라고 불렀고, 날짜 3일을 경계로
`조건만 다른 같은 건` 과 `재게시 후보` 를 갈랐다. 팀이 쓰는 말과 맞지 않았다.

**축을 셋으로 바꿨다. 케이스, 행위자, 포럼.**

| 분류 | 케이스 | 행위자 | 포럼 |
|---|---|---|---|
| 아예 동일 케이스 | 같음 | 같음 | 같음 |
| 재게시 | 같음 | 같음 | 다름 |
| 일부 조건이 다른 같은 케이스 | 같음 | 다름 | 같든 다르든 |

나머지 셋은 그대로다. `같은 대상 의심`, `다른 건`, `확인 못 함`.
여덟에서 여섯이 됐다.

**날짜는 분류 축에서 뺐다.** 며칠 차이인지는 참고로 같이 적는다.
3일 경계는 근거가 없는 값이었다.

**규모로 케이스를 가르지 않는다.** AT&T 에서 49,102,176 과 73,481,539 가
같은 데이터였다. 앞은 고유 이메일 수고 뒤는 행 수다. 규모는 같은지 다른지만
옆에 적고 분류에 쓰지 않는다.

## 도구

`notion_find.py` 에 `--forum` 과 `--size` 를 넣었다. 기존 줄 쪽은 `게시 플랫폼` 과
`주장 규모` 칸에서 읽는다. onion 주소만으로는 포럼을 못 읽는다. 미러마다 앞 해시가
달라서다. 그래서 `--forum` 을 안 주면 재게시와 아예 동일 케이스가 안 갈리고
`확인 못 함` 이 나온다.

`notion_row.py` 가 relation 칸을 쓸 수 있게 했다. `같은 사건: LEAK-8` 처럼 사건 ID 로
주면 그 줄을 찾아 잇는다. 못 찾으면 잇지 않고 확인할 것에 적는다.
